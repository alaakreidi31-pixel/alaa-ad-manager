# ADR 0014: سجل التدقيق (Audit Log) للأحداث الأمنية

- **الحالة:** منفّذ في الخطوة 1.6
- **التاريخ:** 2026-11-15
- **وافقت عليه:** صاحبة المشروع (خطة الخطوة 1.6)

## السياق

المنصة ستحمل بيانات عملاء وأموالاً. عند حدوث شيء مريب (محاولات دخول كثيرة، أو جلسة مسروقة) يجب أن نعرف ماذا حدث، ومتى، ومن أين. وإذا اختُرق التطبيق نفسه، يجب ألا يستطيع المهاجم محو آثاره.

## القرار

**1. جدول `audit_logs`**

- الحدث (`action`)، والمستخدم (`user_id`)، والوقت، وعنوان IP، ونوع الجهاز (User-Agent)، وتفاصيل إضافية (`metadata` بصيغة JSONB).
- **لا يوجد Foreign Key إلى `users`، عن قصد.** السجل التاريخي يجب أن يبقى مهما تغيّرت الحسابات، ولا يجب أن يمنع أي تغيير عليها.
- النصوص الطويلة تُقص إلى 512 حرفاً، حتى لا يملأ طلب واحد الجدول.

**2. السجل للإضافة فقط (Append-only)، بحماية من قاعدة البيانات نفسها**

- الـ migration تسحب من `alaa_app` صلاحيات `UPDATE` و`DELETE` و`TRUNCATE` على هذا الجدول فقط: `REVOKE UPDATE, DELETE, TRUNCATE ON "audit_logs" FROM alaa_app`.
- التطبيق يستطيع الإضافة والقراءة فقط. حتى لو اخترق أحد التطبيق، قاعدة البيانات ترفض تعديل السجل أو حذفه. اختبار في `audit.db-spec.ts` يثبت ذلك.
- الـ migration تفترض وجود المستخدم `alaa_app` في كل بيئة (ADR 0009).

**3. الأحداث المسجّلة** (القائمة الكاملة في `apps/api/src/audit/audit.ts`)

| الحدث                          | متى                                                                        |
| ------------------------------ | -------------------------------------------------------------------------- |
| `auth.login.succeeded`         | اكتمل الدخول وفُتحت جلسة (الطريقة: `password` أو `totp` أو `recovery_code`) |
| `auth.login.password_verified` | كلمة المرور صحيحة، بانتظار رمز 2FA                                         |
| `auth.login.failed`            | رُفض الدخول، والسبب في `metadata.reason`                                    |
| `auth.account.locked`          | قُفل الحساب بعد 5 محاولات خاطئة                                             |
| `auth.two_factor.failed`       | رُفضت الخطوة الثانية، والسبب في `metadata.reason`                           |
| `auth.session.reuse_detected`  | استُخدم refresh token قديم، فأُغلقت كل الجلسات                               |
| `auth.logout`                  | تسجيل خروج                                                                 |
| `admin.two_factor.enabled`     | فُعّل 2FA بالأمر الإداري                                                     |
| `admin.super_admin.created`    | أُنشئ حساب SUPER_ADMIN بالأمر الإداري                                       |

**4. ما لا يُسجَّل أبداً**

- كلمات المرور، والـ tokens، ورموز 2FA، والرموز الاحتياطية، والمفاتيح. اختبار يمر على كل السجل بعد دخول كامل ويتأكد من غيابها.
- البريد يُسجَّل فقط عند محاولة دخول ببريد غير موجود، لأنه لا يوجد `user_id` في هذه الحالة.

**5. الكتابة**

- أحداث الدخول تُكتب عبر `AuditService`. **فشل الكتابة لا يوقف طلب المستخدم**، ويُطبع خطأ في مخرجات الخادم بدون تفاصيل الحدث.
- الأوامر الإدارية تكتب الحدث **داخل المعاملة نفسها (transaction)**: لا يحدث التغيير دون سطره في السجل.

## النتائج

- كل محاولة دخول ناجحة أو فاشلة لها أثر دائم.
- السجل يكبر باستمرار، ولا تنظيف تلقائياً حالياً. سياسة الحذف القديم (retention) تُقرَّر لاحقاً، وتُنفَّذ بمستخدم `alaa_migrator` فقط.
- لا توجد واجهة لعرض السجل بعد. ستأتي في لوحة الإدارة.
- عنوان IP خلف خادم وسيط (proxy) يحتاج إعداد `trust proxy` عند النشر (المرحلة 10). أثناء التطوير يظهر `127.0.0.1`.
