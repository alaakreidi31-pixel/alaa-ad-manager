# ADR 0023: الإشعارات داخل التطبيق

- **الحالة:** منفّذ (الخطوات 9.1 إلى 9.3).
- **التاريخ:** 2026-11-16
- **وافقت عليه:** صاحبة المشروع، بعد مراجعة SQL ونتائج 23 فحصاً، ثم تعديل `ON DELETE CASCADE`.

## قرارات صاحبة المشروع

- داخل التطبيق فقط (بلا بريد إلكتروني الآن)، للإدارة وللعميل.
- الأحداث: الفواتير، والمهام، والحملات، والأمان.

## القرار

**1. الجدول `notifications`**: صف لكل مستخدم. نوع الإشعار رمز (`invoice.issued`) مع قيمه، والواجهة تكتب الجملة بلغة المستخدم. لا كلمة مرور ولا رمز ولا ملاحظة داخلية ولا نص تعليق أبداً.

- الرابط مسار داخل التطبيق فقط (يُرفض `https://...` و`//...`)، والواجهة تتحقق منه مرة ثانية.
- مفتاح عدم التكرار: الحدث المتكرر يظهر مرة واحدة لكل مستخدم.
- لا حذف ولا تعديل: التغيير الوحيد "تمت القراءة"، ووقتها تضعه قاعدة البيانات مرة واحدة.
- الإشعار يتبع صاحبه (`ON DELETE CASCADE`): التطبيق لا يحذف الحسابات أبداً، لكن الاختبارات التي تفرغ جدول المستخدمين لا تُمنع.

**2. من يستلم**: إشعار الإدارة لكل `SUPER_ADMIN` نشط، وإشعار العميل لحسابات **ذلك العميل** النشطة فقط. كل مسارات `/api/notifications` تعمل على إشعارات صاحب الجلسة فقط (اختبار IDOR).

**3. الأحداث**

- فورية (في نفس transaction الحدث): فاتورة صدرت، دفعة سُجّلت، حالة حملة (إلا الأرشفة)، مهمة مشتركة جديدة أو تغيّرت حالتها، استيراد CSV، قفل حساب، دخول من جهاز جديد.
- دورية (مع مزامنة المهام، مرة في الدقيقة على الأكثر عند فتح الجرس): مسودة فاتورة، فاتورة متأخرة، حملة بلا أرقام، مهمة متأخرة، مهام مشتركة متكررة.
- "جهاز جديد": متصفح لم يُستعمل في أي دخول ناجح سابق لهذا الحساب. أول دخول للحساب ليس "جديداً".

**4. الواجهة**: جرس في أعلى كل صفحة بعدد غير المقروء (يتحدث كل دقيقة)، وصفحة `/notifications`.
