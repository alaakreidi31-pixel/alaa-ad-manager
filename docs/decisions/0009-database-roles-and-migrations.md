# ADR 0009: صلاحيات قاعدة البيانات والـ migrations والتراجع

- **الحالة:** منفّذ
- **التاريخ:** 2026-11-14
- **طلبته:** صاحبة المشروع، ضمن تحسينات خطة الخطوة 1.1

## السياق

مع أول جدول (`users`) احتجنا طريقة آمنة لتغيير بنية القاعدة، واختبارها، والتراجع عنها عند الطوارئ. طلبت صاحبة المشروع فصل صلاحيات الـ migrations عن مستخدم التطبيق، وألا يُنفَّذ أي تراجع تلقائياً على قاعدة حقيقية.

## القرار

**1. مستخدمان منفصلان**

| المستخدم        | يستخدمه                                                            | الصلاحيات                                                                                        |
| --------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| `alaa_migrator` | أوامر Prisma فقط، عبر `MIGRATE_DATABASE_URL` في `prisma.config.ts` | يملك القاعدتين، ويغيّر البنية، ومعه `CREATEDB` للقاعدة المؤقتة                                    |
| `alaa_app`      | الخادم أثناء التشغيل، عبر `DATABASE_URL`                           | SELECT وINSERT وUPDATE وDELETE فقط، تُمنح تلقائياً على كل جدول جديد عبر `ALTER DEFAULT PRIVILEGES` |

مُختبَر: `alaa_app` لا يستطيع إنشاء جدول ولا حذف `users`.

**2. إنشاء الـ migrations**

- `prisma migrate dev --create-only` أولاً، ثم **مراجعة ملف SQL مع صاحبة المشروع**، ثم التطبيق.
- ما لا يدعمه Prisma (مثل شروط `CHECK`) يُضاف يدوياً في ملف SQL، مع تعليق يوضّح أنه مضاف باليد.
- نتبع مبدأ **"نصلح للأمام"**: الخطأ في migration يُعالَج بـ migration جديدة.

**3. التراجع**

- لكل migration ملف تراجع في `apps/api/prisma/rollbacks/<name>.down.sql`، كخطة طوارئ.
- **لا يُنفَّذ أي ملف تراجع تلقائياً على قاعدة حقيقية.** ينفّذه تلقائياً فقط `pnpm test:rollback`، وعلى قاعدة ينتهي اسمها بـ `_test`.
- تنفيذه يدوياً على قاعدة التطوير أو الإنتاج يحتاج موافقة صاحبة المشروع.

**4. قاعدة الاختبار**

- الحارس `assertTestDatabaseUrl()` يرفض أي قاعدة لا ينتهي اسمها بـ `_test`، ولا يُظهر كلمة المرور في رسائله.
- قبل الاختبارات: `prisma migrate deploy` على قاعدة الاختبار (يضيف فقط، لا يمسح).
- **لا نستخدم `prisma migrate reset`**: يحذف مخطط `public` ويعيد إنشاءه، فتضيع صلاحيات `alaa_app`.
- كل اختبار ينظّف الصفوف بنفسه.

**5. CI**

PostgreSQL 17 كـ service container، يُجهَّز بنفس المستخدمَين والصلاحيات، بكلمات مرور مؤقتة ليست أسراراً.

## البدائل التي لم تُختر

- **مستخدم واحد لكل شيء:** أبسط، لكن اختراق الخادم يعني القدرة على حذف الجداول.
- **`prisma migrate reset` للاختبارات:** يضيّع الصلاحيات كما ذُكر.

## النتائج

- ثلاث كلمات مرور على جهاز التطوير: `postgres` و`alaa_migrator` و`alaa_app`.
- ملف `.env` يحتوي رابطَي `alaa_migrator`. على خادم الإنتاج لاحقاً يجب ألا تكون بيانات `alaa_migrator` متاحة للخادم أثناء التشغيل.
- `updated_at` يحدّثه Prisma وليس القاعدة، فالتعديل بـ SQL مباشر لا يحدّثه.

## متى نراجعه

قبل أول نشر على خادم حقيقي: فصل بيانات `alaa_migrator` عن بيئة تشغيل الخادم.
